# SwimFind 개발 로드맵

기준일: 2026-10-06

이 문서는 기존 제품·엔지니어링 기준을 바탕으로 개발 순서와 단계별 완료 기준을 정리한다.
확정된 출시 일정이 아닌 권장 작업 순서이며, 각 단계는 기능 단위 Issue로 나누어 진행한다.

현재 개발 방식은 **애플리케이션 골격 → 공용 UI 기본 준비 → 모든 MVP 화면의 mock UI/UX 확인 → 필요 필드 확인과 스키마 보완 → 실제 데이터·기능 연결 → 통합 검증·배포**이다.
mock 데이터는 실제 저장 없이 화면과 사용자 흐름을 확인하기 위해 코드 안에 둔 임시 데이터이며, 화면은 실제 경로에 구현한다.
화면에서 확인한 필요 필드를 바탕으로 DB schema를 변경하므로, schema는 해당 단계 전에 미리 확정하지 않는다.
이미 구현한 DB·migration·Repository·Service·상세 조회 코드는 유지한다.

## 1. 개요

SwimFind는 사용자가 로그인하지 않아도 지역·수영장 이름·현재 위치를 기준으로 수영장을 찾고, 오늘 자유수영이 가능한지 확인해 방문 여부를 판단하도록 돕는 서비스다.

주요 기능:

- **오늘 자유수영 상태**: 일정·휴관·운영 정보로 오늘 이용 가능 여부를 계산해 보여준다.
- **수영장 탐색**: 이름·지역·현재 위치로 검색하고 검색 결과에서 후보를 비교한다.
- **수영장 상세**: 오늘 회차·가격·이용 조건·휴관·정보 출처와 확인일을 제공한다.
- **관심 수영장**: 로그인한 사용자가 저장한 수영장의 현재 오늘 상태를 다시 확인한다.
- **후기와 정보 제보**: 이용 경험을 공유하고 잘못된 정보를 제보하며, 운영자가 검토한다.

### 문서와 구현의 차이

- CI는 `pnpm check`·`pnpm typecheck`·`pnpm test --run`·`pnpm build`를 실행한다. Vitest는 별도 설정 파일 없이 테스트를 자동 탐색한다.
- 상세 조회 연결은 구현됐지만, 오늘 남은 시간과 입장 마감·회차 조건·정보 출처·확인일을 중심으로 한 상세 화면은 아직 완성되지 않았다.
- 상태 계산에는 수영장 자체 비활성 상태, 입장 마감, 부분 운영 변경, 정보 최신성 판단이 아직 충분히 반영되지 않았다.
- 현재는 회차가 없으면 일반 운영시간을 계산에 사용한다. 시간표 누락과 운영시간 전체 자유수영을 어떻게 구분할지 추가 검토가 필요하다. 동남스포피아 seed는 확인된 전체 이용 시간 범위를 회차에 저장하는 현재 방식을 유지한다.
- `architecture.md`의 폴더 구조에는 `components/layout`(헤더·Footer·페이지 컨테이너), `features/*/mocks`(mock 데이터), 운영자 경로 `/admin`이 없다. 단계 2에서 구조 문서 갱신을 별도로 제안한다.
- Figma 홈·Footer에는 `ia.md`에 없는 항목(인기 키워드·거리순 정렬·약관류 링크)이 있다. 디자인대로 구현하기로 했으며, 해당 화면 작업 때 `ia.md` 갱신을 제안한다.

위 차이는 남은 작업으로 기록한다. 이 문서 작성만으로 기존 설계나 데이터 처리 규칙을 변경하지 않는다.

## 3. 개발 워크플로우

1. **작업 계획**
   - 기존 코드와 관련 `docs/`를 읽고 현재 상태를 파악한다. 문서만 보고 구현 상태를 추측하지 않는다.
   - 새로운 작업이 생기면 이 로드맵에 반영한다. 우선순위 작업은 마지막으로 완료한 작업 다음에 둔다.

2. **작업 생성**
   - 한 번에 다음 기능 하나를 선택하고, 왜 필요한지 → 무엇을 만들지 → 어떻게 구현할지 설명한다.
   - Issue는 저장소 템플릿(기능 작업)을 따라 목표·포함·제외·완료 기준을 적고, 선행 작업·관련 파일·검증 항목을 함께 적는다. 별도 Task 파일을 자동으로 만들지 않고 Issue와 로드맵을 사용한다.
   - 상태 계산 같은 비즈니스 로직 작업은 Vitest 테스트 항목을 완료 기준에 포함한다.

3. **작업 구현**
   - 코드를 작성하기 전에 변경할 파일·내용·순서를 설명하고 사용자 승인을 받는다.
   - 승인된 범위만 구현하고, 후속 단계의 기능을 미리 구현하지 않는다.
   - `pnpm check`, `pnpm typecheck`, `pnpm test --run`, `pnpm build`로 검증한다.
   - 화면·흐름을 바꾸는 작업은 **브라우저 확인을 필수**로 한다. Claude in Chrome 또는 Playwright MCP로 화면 렌더링·콘솔 오류·키보드 동작·모바일/데스크톱 크기를 확인하고 결과를 PR의 확인 사항에 적는다. 도구가 연결되지 않았으면 연결을 요청하고, 확인하기 전에는 해당 항목을 완료로 표시하지 않는다.
   - 각 단계가 끝나면 결과·검증·변경 파일·미확인 사항을 보고하고 추가 지시를 기다린다.
   - 커밋·push는 승인 후에만 진행한다. 관련 테스트를 기능 커밋에 포함하고 한국어 Conventional Commit을 사용한다. Issue·PR은 실제 저장소 템플릿을 따른다.
   - migration은 schema 수정 → generate → SQL 검토 → 개발 DB migrate → 실제 DB 확인 순서로 진행한다. 적용된 migration은 수정·삭제하지 않는다.

4. **로드맵 업데이트**
   - 체크박스는 검증 후 `[x]`로 갱신한다. 기능 작업으로 정책이 바뀌면 관련 기준 문서와 이 로드맵의 상태도 함께 검토한다.
   - PR에는 실제 수행한 검사와 미확인 항목을 구분한다. mock 화면 완료·실제 기능 연결·로컬 검증·main 병합·배포를 같은 완료 상태로 취급하지 않는다.

## 4. 개발 단계

참고 자료의 개발 단계 흐름만 활용하고, 화면·데이터·기술 선택은 SwimFind 기준 문서를 따른다.
골격과 공용 UI를 먼저 갖춘 뒤 모든 화면의 UI를 mock 데이터로 검토하고, 필요 필드를 확인해 schema를 보완한다. 실제 기능 연결은 공개 탐색 → 인증·관심 → 후기 → 제보 순서로 진행한다.
각 단계 안에서도 한 번에 한 작업만 수행한다. 이전 단계가 끝나기 전에 다음 단계 작업을 시작하지 않고, 후속 단계의 서버 기능을 미리 구현하지 않는다.

### 단계 1 — 기존 기반 확인과 작업 준비

왜: 이미 만든 기반을 다시 만들지 않고, 화면 검토와 실제 기능 연결의 출발점을 명확히 한다.

무엇을·어떻게:

- [x] 현재 상세 페이지의 정상 조회·없는 ID의 404·요일/가격/운영시간 표시를 브라우저에서 최종 확인한다.
- [x] 2절의 구현 상태와 미확인 사항을 갱신한다. 기존 schema·migration·seed를 임시 화면용으로 변경하지 않는다.
- [x] 기존 조회 타입을 바탕으로 UI가 받을 데이터와 mock 시나리오를 정리한다. 아직 없는 후기·제보 등의 화면 타입은 해당 화면을 만들 때 최소 범위로 정의한다.
- [x] 초기 CI와 main 보호를 준비한다. 수동 Preview의 상세 조회와 환경변수 범위 확인을 마쳤고 Issue #18을 닫았다.

로컬 UI 개발은 CI와 main 보호가 준비된 상태에서 단계 2로 진행할 수 있다.

완료 기준: 구현·검증·병합·배포 상태를 구분하고, 기존 실제 조회 흐름을 유지한 채 UI 개발을 시작할 수 있다.

### 단계 2 — 애플리케이션 골격

왜: 모든 화면의 경로·공통 레이아웃·이동 구조와 화면이 사용할 타입을 먼저 갖춰, 이후 화면 작업이 같은 틀에서 진행되게 한다. 골격이 완성되기 전에는 화면 UI 작업을 시작하지 않는다.

무엇을·어떻게:

- [ ] `architecture.md`의 경로(`/pools`, `/favorites`, `/reviews`, `/reviews/write`, `/reports`, `/login`, `/my`)와 운영자 경로 `/admin` 아래의 제보 검토 목록·상세 빈 페이지를 만든다. 기존 `/`, `/pools/[poolId]`는 유지한다.
- [ ] `components/layout`에 헤더·내비게이션·Footer·페이지 컨테이너 골격을 만든다. Figma 헤더 기준: 로고·수영장 찾기·관심 수영장·마이페이지·로그인.
- [ ] 화면용 view-model 타입을 `features/*/*.types.ts`에 정의한다. 대상은 수영장 목록 카드, 상세 보조 영역(이미지·시설·FAQ·강습·후기 요약), 후기, 제보, 관심이다. 기존 `PoolDetailResult`·Drizzle 기반 타입을 재사용하고, 아직 없는 도메인은 UI에 필요한 최소 타입만 정의한다.
- [ ] `/pools` 검색 조건(이름·지역·필터) 타입을 정의한다. URL `searchParams`와의 변환은 단계 5에서 연결한다.
- [ ] 로그인 전후 화면 확인용 mock 사용자 타입(비로그인·회원·운영자)을 정의한다. 실제 세션 모델은 단계 7에서 설계한다.
- [ ] 여러 도메인이 공유하는 타입만 `shared/types`에 둔다. 컴포넌트 Props 타입은 해당 컴포넌트 파일에 함께 정의한다.
- [ ] 위 타입은 UI 검토용 임시 타입이다. DB schema·API 응답·전역 상태를 미리 확정하지 않으며, 단계 5에서 실제 타입으로 교체한다.
- [ ] `architecture.md`에 `components/layout`·`features/*/mocks`·`/admin` 경로를 추가하는 문서 갱신을 별도로 제안한다.

완료 기준: 모든 MVP 경로가 열리고 공통 레이아웃으로 이동할 수 있으며, 화면용 타입이 정의되어 타입 검사·빌드를 통과한다. 기존 상세 조회·404 동작은 유지한다. 화면 내용은 포함하지 않는다.

### 단계 3 — 공용 UI 기본 준비

왜: 화면을 구현하기 전에 입력·버튼·상태 표현의 일관된 기반이 필요하다. 모든 공용 UI를 미리 만들지 않고 기본 6종부터 준비한 뒤, 나머지는 해당 화면을 만들 때 추가한다.

무엇을·어떻게:

- [ ] Figma 기준으로 색상·spacing·radius·typography·상태 색 토큰을 최소 세트로 정리한다. 이후 토큰은 처음 쓰는 컴포넌트 작업에서 함께 추가한다.
- [ ] Noto Sans KR(`next/font`)과 `lang="ko"`를 적용한다.
- [ ] `Button`, `Input`, `Textarea`, `Badge`, `Card`, `Avatar`를 먼저 준비한다.
- [ ] `Chip`, `Toggle`, `Tabs`, `Select`, `Modal`, `Toast`와 로딩 표시·Skeleton·빈 상태·오류 안내 UI는 기본 6종 이후 해당 화면을 만들 때 추가한다.
- [ ] 공용 UI는 `components/ui`에 도메인을 모르는 형태로 평평하게 두고(컴포넌트마다 폴더 하나), 도메인 UI는 `features`에 둔다. CSS Modules·CSS Variables를 사용하고, CVA는 variant가 여러 개인 컴포넌트에만, 단순 조건에는 clsx를 사용한다.
- [ ] 기본·포커스·비활성·오류·처리 중 등 해당 컴포넌트에 필요한 상태를 확인한다. Modal은 키보드 조작·포커스 이동과 복귀·닫기 동작을 확인한다.
- [ ] 모바일은 Figma 데스크톱 디자인을 기준으로 단순 세로 배치부터 시작한다. 별도 모바일 디자인이 정해지기 전에는 임의로 디자인하지 않는다.

완료 기준: 기본 6종이 토큰만으로 스타일링되어 화면에 조합할 수 있다. 별도의 공용 UI 검토 화면은 만들지 않고, 모바일·데스크톱·키보드 환경의 기본 동작은 단계 4의 실제 화면에서 함께 확인한다. 공용 UI는 수영장 상태 계산이나 DB 접근을 포함하지 않는다.

### 단계 4 — 모든 MVP 화면의 mock UI/UX 확인

왜: schema와 서버 기능을 확정하기 전에 화면의 정보 우선순위와 이동 흐름을 mock 데이터로 빠르게 검토하고, 화면에 필요한 데이터 필드를 확인한다. 화면은 실제 경로에 구현하며 역할별(비로그인·회원·운영자)로 정리한다.

무엇을·어떻게:

- [ ] 비로그인 — 공개 탐색: 홈·검색 결과·상세 화면을 만들고 이름·지역·현재 위치 탐색 진입과 상세 이동을 확인한다. 홈은 Figma 기준으로 구현하며, `ia.md`에 없는 인기 키워드·거리순 정렬·약관류 링크도 디자인대로 표현하고 해당 시점에 `ia.md` 갱신을 제안한다.
- [ ] 비로그인 — 상세 보조 영역: 전체 일정·일반 운영시간·가격·이용 조건·휴관·출처·확인일·이미지·시설·FAQ·강습 안내·후기 요약을 표현한다.
- [ ] 비로그인 — 로그인: 로그인 화면과 로그인 후 원래 화면 복귀를 표현한다.
- [ ] 회원 — 개인 기능: 관심 목록·마이페이지와 로그인 전후 화면을 표현한다. 로그인 전후는 로컬 환경변수로 mock 사용자를 설정해 확인하며, 가짜 로그인 UI는 만들지 않고 Preview·Production에는 설정하지 않는다.
- [ ] 회원 — 후기: 목록·작성·수정·작성 완료·삭제 확인·작성자 프로필·다른 후기·내 후기를 표현한다.
- [ ] 회원 — 제보: 정보 수정 제보·미등록 수영장 등록 요청·접수 결과·내 제보·검토 상태를 표현한다.
- [ ] 운영자(`/admin`): 제보 목록·내용 비교·승인/반려 흐름을 표현한다. 별도 통계 대시보드 등은 추가하지 않는다.
- [ ] Figma에 없는 화면(운영자 검토, 후기 작성·수정·삭제 확인 등)은 기존 디자인 시스템(토큰·공용 UI)을 따라 새로 설계하고 화면별로 승인받는다.
- [ ] 상세 `/pools/[poolId]`는 이 단계 동안 mock 데이터를 사용한다. 화면은 props 기반으로 분리하고, 실제 조회 코드(Service·Repository·ID 검증·테스트)는 삭제하지 않고 단계 5에서 다시 연결한다. 이 기간 `/pools/1~3`과 Preview는 mock 화면이며 실제 정보가 아니다.
- [ ] mock 데이터는 `features/*/mocks`에 두고 단계 2의 타입을 따른다. 종료·휴관·미확인·가격 없음·입장 마감 없음 등 까다로운 사례를 포함하며, 실제 정보로 오해되지 않도록 구분하는 방법은 구현 전에 제안한다.
- [ ] `PoolCard`, `PoolStatusBadge` 등 도메인 UI는 `features`에 두고 공용 UI를 조합한다. 필요한 공용 UI(`Chip`·`Toggle`·`Tabs`·`Select`·`Modal`·`Toast`·Skeleton 등)는 이 단계에서 추가한다.
- [ ] 정상·로딩·빈 목록·조회 실패·정보 미확인·휴관·종료·로그인 필요·폼 오류·제출 실패 시나리오를 확인한다.
- [ ] 모바일은 단순 세로 배치부터 시작하고 데스크톱·키보드 접근을 확인한다. 검색 조건·뒤로가기·입력 유지·다음 행동을 점검한다.
- [ ] 화면별로 필요하지만 현재 DB에 없는 필드(지역·거리·인기 키워드·대표 이미지 등)를 기록한다. 이 기록은 단계 5의 schema 변경 근거다.

완료 기준: 모든 MVP 화면과 주요 행동을 mock으로 확인하고 UI 피드백을 반영했으며 필요 필드 목록을 정리했다. 이 완료는 실제 로그인·조회·저장·업로드 기능의 완료를 뜻하지 않는다.

### 단계 5 — 스키마 보완·공개 탐색 실제 연결·오늘 이용 정보 정책

왜: 단계 4에서 확인한 필요 필드를 DB에 반영하고, mock으로 확인한 핵심 경험을 실제 DB의 수영장 데이터로 제공하며 잘못된 이용 판단을 막는다.

무엇을·어떻게:

- [ ] 단계 4에서 기록한 필요 필드를 바탕으로 schema 변경안을 제안한다. 승인 후 schema 수정 → generate → SQL 검토 → 개발 DB migrate → 실제 DB 확인 순서로 진행하며, 적용된 migration은 수정·삭제하지 않는다. 개발 seed 추가가 필요하면 별도 승인으로 제안한다.
- [ ] 단계 2의 임시 화면용 타입을 실제 DB 기반 타입으로 교체한다.
- [ ] 홈의 이름·지역 검색과 `/pools` 검색 결과를 Repository·Service에 연결한다. 검색 조건은 URL `searchParams`에 유지한다.
- [ ] 지역 검색은 현행 주소 데이터로 가능한 범위부터 구현하고, mock 검색 결과를 실제 결과로 교체한다.
- [ ] 목록에서도 같은 Service의 오늘 상태를 사용한다. 필요한 데이터를 목록 조회에 함께 가져오고, 수영장마다 상세 조회를 반복 호출하는 방식은 피한다.
- [ ] 상세를 다시 실제 조회에 연결하고(단계 4 동안은 mock 사용), 오늘 적용 일정과 남은 이용 시간을 Service에서 구성한다.
- [ ] 비활성 수영장의 공개 조회 정책, 시간표 누락, 입장 마감·회차별 조건, 전일 휴관·부분 운영 변경을 검토하고 계산·표시에 반영한다.
- [ ] `UNKNOWN`·`NOT_OPERATED`를 구분한다. 정보가 부족하면 `UNVERIFIED`, 일정 없음이 확인된 근거가 있을 때만 `NO_SCHEDULE`을 사용한다.
- [ ] 정보 출처·확인일·공식 홈페이지를 표시한다. 정보 최신성 판단 기준과 필요한 검증 데이터는 별도로 합의한다.
- [ ] 일정 적용 기간·휴관 우선순위·시작/종료·입장 마감 경계 테스트를 보완하고, 실제 조회의 로딩·빈 결과·오류·404를 확인한다.

완료 기준: 로그인 없이 홈 → 검색 → 상세 흐름을 실제 데이터로 이용할 수 있다. 사용자가 오늘 시간·가격·조건·예외를 확인할 수 있고 주요 판단 규칙이 테스트로 검증된다.

### 단계 6 — 위치·이미지·보조 정보 실제 연결

왜: 화면에 표현한 위치·시설 등의 정보를 실제 탐색과 방문 판단에 사용할 수 있게 한다.

무엇을·어떻게:

- [ ] Browser Geolocation API와 우리 DB의 좌표로 주변 탐색을 구현한다.
- [ ] NAVER Maps는 DB 검색 결과의 지도 표시와 위치 확인에 사용한다.
- [ ] 위치 권한 거부 시 지역 직접 선택으로 이어지도록 한다.
- [ ] 이미지·시설·공식 안내·길찾기를 연결하고, 단계 4의 이미지·시설 mock 데이터를 개발 seed와 조회 경로로 교체한다. 확인되지 않은 정보는 mock 대신 미확인 상태로 표시한다.
- [ ] FAQ·강습 안내는 핵심 정보보다 낮은 우선순위로 연결하고 단계 4의 mock 데이터를 교체한다. 필요한 데이터 구조는 실제 확인된 요구사항에 맞춰 설계한다.

완료 기준: 이름·지역·현재 위치로 후보를 비교할 수 있고, 위치 권한을 거부해도 핵심 흐름을 이용할 수 있다. 시간표상 이용 가능을 실시간 입장 보장으로 표현하지 않는다.

### 단계 7 — 인증·관심 수영장 실제 연결

왜: 검토한 로그인·관심 UI를 실제 사용자별 데이터와 안전하게 연결한다.

무엇을·어떻게:

- [ ] Better Auth와 필요한 사용자·세션 모델을 설계하고 migration을 검토한다.
- [ ] 로그인·로그아웃과 원래 화면 복귀를 구현한다.
- [ ] 관심 수영장 등록·해제·목록을 구현하고 사용자와 수영장 조합의 중복을 막는다.
- [ ] 서버에서 인증과 소유권을 확인하고, 목록은 저장 당시가 아닌 현재의 오늘 상태를 표시한다.
- [ ] 마이페이지의 기본 프로필·관심 목록 진입점을 연결한다.
- [ ] 단계 4의 로그인·관심·마이페이지 mock 화면을 실제 인증·데이터로 교체하고 mock 사용자 환경변수를 제거한다.

완료 기준: 공개 탐색은 계속 비로그인으로 이용 가능하며, 로그인 사용자는 자신의 관심 수영장을 저장·해제·재조회할 수 있다.

### 단계 8 — 후기·이미지 실제 연결

왜: 공식 안내만으로 알기 어려운 실제 이용 경험으로 방문 판단을 보완한다.

무엇을·어떻게:

- [ ] 후기·후기 이미지 모델과 조회·작성·수정·삭제 권한을 구현한다.
- [ ] 후기 조회는 공개하고, 작성·변경은 로그인한 작성자에게 허용한다.
- [ ] React Hook Form·Zod를 이 단계에서 설치해 적용하고(단계 9의 제보 폼에서도 사용), 변경은 Server Action → 검증 → Service → Repository로 처리한다. 단계 4의 폼 화면은 라이브러리 없이 입력·오류 상태만 표현한다.
- [ ] S3 presigned URL로 이미지 업로드를 구현하고 파일 제한·사용자 소유권·후기당 최대 5장을 검증한다.
- [ ] 작성자 프로필·다른 후기, 마이페이지의 내 후기를 연결한다.
- [ ] 제출 실패 시 입력을 유지하고 중복 제출을 방지한다.
- [ ] 단계 4의 후기 요약·후기 mock 화면을 실제 데이터로 교체한다.

완료 기준: 비로그인 사용자는 후기를 읽을 수 있고, 작성자는 자신의 후기를 관리할 수 있다. 과거 혼잡 경험을 실시간 혼잡 정보로 표시하지 않는다.

### 단계 9 — 정보 제보·운영자 검토 실제 연결

왜: 운영 정보의 오류와 변경을 수집하고, 검증된 데이터만 공식 정보로 제공한다.

무엇을·어떻게:

- [ ] 로그인 사용자의 정보 수정 제보와 미등록 수영장 등록 요청을 구현한다.
- [ ] 근거·수정 제안·처리 상태를 저장하고 마이페이지에서 내 제보를 조회한다.
- [ ] 운영자의 검토·승인·반려 절차와 권한을 구현한다.
- [ ] 승인 후 공식 정보와 확인일은 검증을 거쳐 별도로 수정한다. 제출만으로 자동 반영하지 않는다.
- [ ] 단계 4의 제보 mock 화면과 `/admin` 운영자 검토 mock 화면을 실제 데이터와 권한으로 교체한다.

완료 기준: 접수 성공과 검토 완료가 구분되며, 미검증 제보는 공식 정보로 노출되지 않는다.

### 단계 10 — 통합 검증과 출시 준비

왜: 개별 기능의 정상 동작뿐 아니라 실제 사용자 흐름과 운영 환경을 검증한다.

무엇을·어떻게:

- [ ] 홈 → 검색 → 상세 → 오늘 이용 정보 확인을 Playwright로 검증한다.
- [ ] 로그인 복귀·관심 저장·후기 작성·제보 접수와 각 흐름의 실패·재시도를 검증한다.
- [ ] 미확인·휴관·종료·위치 권한 거부·없는 ID·권한 없는 변경 등 주요 예외를 확인한다.
- [ ] 모바일·키보드 접근·이미지·쿼리·메타데이터·SEO·성능을 점검하고 실제 측정 결과에 따라 개선한다.
- [ ] 운영 DB·초기 import·migration 적용 및 복구 절차·환경 변수·Vercel Production 배포를 확인한다.
- [ ] Sentry·PostHog를 필요한 범위에서 연결하고, 배포 후 핵심 흐름을 다시 확인한다.
- [ ] 공개 환경에 mock 데이터(`features/*/mocks`)·mock 사용자 환경변수·가짜 로그인·가짜 제출 성공이 남아 있지 않은지 확인한다.

완료 기준: 공개할 기능이 실제 운영 데이터와 권한 기준으로 동작하고, 핵심 흐름·주요 예외·오류 추적·배포 상태를 확인했다.

## 6. mock 데이터와 실제 연결의 경계

- 단계 1-C에서 기존 `PoolDetailResult`의 기본 정보·오늘 상태·운영시간·일정·회차·휴관·요금과 화면 표시 여부를 대조했다. 상세 계약에 없는 이미지·시설·후기·제보는 해당 기능 단계에서 연결한다.
- `null`은 값 미확인, 빈 배열은 조회된 row 없음으로 구분한다. 가격 기록 없음은 무료가 아니며, 입장 마감은 값이 있는 회차에만 표시한다.
- `NO_SCHEDULE`은 현재 상태 계산 함수가 반환하지 않는 UI 검토 시나리오다. 입장 마감에 따른 상태 변경과 부분 운영 변경은 단계 5에서 검토한다.

- mock 데이터는 코드 안 `features/*/mocks`에 둔다. 화면은 실제 경로에 구현하고, 별도 mock 페이지·mock 전환 스위치·MSW 같은 라이브러리는 두지 않는다. MSW 등은 클라이언트 조회나 네트워크 응답 고정이 필요해질 때 재검토한다.
- 서버 Repository·Service에 가짜 row를 넣거나 DB에 mock 행을 넣지 않는다. 테이블이 있는 데이터(수영장·일정·요금 등)가 더 필요하면 개발 seed 추가를 별도 승인으로 제안하고, 개발 seed는 운영 DB에서 실행되지 않도록 단계 10에서 분리한다.
- 기존 Drizzle 기반 타입을 재사용하고 mock도 그 모양을 따른다. 아직 없는 도메인은 UI에 필요한 최소 타입만 정의한다. 전체 DB 모델·API 응답·전역 상태를 미리 확정하지 않는다.
- 화면이 받을 데이터와 사용자 동작을 분리해, 실제 연결 시 UI를 다시 만들지 않고 조회·저장 부분을 교체할 수 있게 한다. 과도한 공통 provider나 저장소 추상화는 추가하지 않는다.
- 상태 mock은 시나리오별로 준비한다. UI에 자유수영 상태 계산을 새로 구현하지 않고, 실제 연결 후에는 Service 결과를 사용한다.
- 상세 `/pools/[poolId]`는 단계 4 동안 mock 데이터를 사용하되, 실제 조회 코드(Service·Repository·ID 검증·테스트)는 삭제하지 않고 단계 5에서 다시 연결한다. 이 기간의 mock 화면은 실제 정보가 아니며 Preview에도 노출될 수 있다.
- 로그인 전후 화면은 로컬 환경변수 mock 사용자로 확인한다. 가짜 로그인 UI는 만들지 않고 Preview·Production에는 설정하지 않는다. 저장·업로드·운영자 검토는 화면 행동만 모의하며 실제 인증·DB 반영으로 오해되지 않도록 구분한다.
- 공개 탐색 화면부터 개인 화면·운영자 검토까지 모두 mock으로 확인하되, 기능 연결은 단계 5~9 순서를 따른다.
- UI 검토 중 화면별로 필요한 필드를 기록하고 단계 5에서 schema 변경을 제안한다. DB schema 변경은 별도 승인·migration 절차를 거쳐 진행한다.

- [ ] 운영 연결 시: main → Vercel Production 자동 배포를 확인한다. 실제 사용자에게 공개하는 범위는 해당 단계의 완료 기준을 충족한 기능으로 정한다.

## 10. 주의사항

### 구조 우선 접근법

1. **골격을 완료한 뒤 화면 UI를 시작한다.** 경로·레이아웃·타입이 정해지기 전에는 화면 작업을 시작하지 않는다.
2. **mock으로 전체 UI를 확인한 뒤 schema를 설계한다.** 단계 4에서 필요 필드를 기록하고 단계 5에서 변경한다.
3. **공통 컴포넌트를 먼저 준비하되 필요한 만큼만 만든다.** 기본 6종을 먼저 만들고 나머지는 해당 화면에서 추가한다.
4. **UI 피드백을 반영한 뒤 백엔드를 연결한다.** 후속 단계의 서버 기능을 미리 구현하지 않는다.

### 테스트와 검증

1. 잘못된 오늘 상태를 보여주지 않는 단위 테스트(Vitest)를 우선한다. 일정 적용 기간·휴관 우선순위·시작/종료·입장 마감 경계를 포함한다.
2. 화면·흐름 변경은 브라우저에서 확인하고(Claude in Chrome 또는 Playwright MCP) 결과를 PR에 기록한다.
3. 정상 경로뿐 아니라 빈 결과·조회 실패·404·권한 없음 등 에러 상황도 확인한다.
4. 단계가 바뀔 때 CI 통과와 이전 단계의 핵심 흐름을 다시 확인한다.

### 정보 표현 원칙

- 오늘 상태는 화면에서 계산하지 않고 Service 결과를 사용한다.
- 정보 미확인을 이용 불가로, 가격 기록 없음을 무료로 표현하지 않는다.
- 시간표상 이용 가능을 실시간 입장 보장으로 표현하지 않는다.
- 성능은 수치 목표를 미리 정하지 않고 단계 10의 실제 측정 결과를 바탕으로 정한다.

## 12. MVP 이후 검토

예약·결제, 강습 전용 검색·추천, 운동 기록, 커뮤니티·채팅, 실시간 혼잡도 등은 [MVP 제외 범위](product/mvp.md#15-out-of-scope)에 따라 보류한다.

새 기능은 “오늘 갈 수 있는 수영장을 찾는 데 직접 도움이 되는가?”와 실제 사용자 요구를 기준으로 검토한다. 전체 화면의 mock 검토를 먼저 하더라도 공개 탐색의 실제 연결이 핵심 경험의 첫 완료 지점이며, 개인화·후기·제보의 실제 연결은 제품 문서의 후속 MVP 순서를 따른다.

참고 자료는 개발 진행 단계에만 활용한다. 기술·테스트·품질 기준과 출시 범위는 SwimFind 문서를 따르며, 일정과 성능 목표는 실제 작업 범위와 측정 결과를 바탕으로 정한다.
