# SwimFind 개발 로드맵

기준일: 2026-10-05

이 문서는 기존 제품·엔지니어링 기준을 바탕으로 개발 순서와 단계별 완료 기준을 정리한다.
확정된 출시 일정이 아닌 권장 작업 순서이며, 각 단계는 기능 단위 Issue로 나누어 진행한다.

현재 개발 방식은 **확장 공용 UI 준비 → 모든 MVP 화면의 mock UI/UX 확인 → 실제 데이터·기능 연결 → 통합 검증·배포**이다.
mock은 실제 저장 없이 화면과 사용자 흐름을 확인하기 위한 임시 데이터다.
이미 구현한 DB·migration·Repository·Service·상세 조회는 유지한다.


## 2. 현재 구현 상태

아래 상태는 `main`의 `f679493` 커밋과 단계 1 작업 A~C의 확인 결과 기준이다.
구현·로컬 검증·`main` 병합과 Preview·Production 배포는 구분한다. 배포 상태는 아직 확인하지 않았다.

| 영역 | 현재 상태 |
|---|---|
| 기본 개발 환경 | Next.js App Router, TypeScript, pnpm, Biome 설정 |
| 스타일링 기반 | CSS Variables 토큰과 전역 import 준비, CSS Modules 사용, CVA·clsx 설치 |
| DB 기반 | PostgreSQL/Neon 연결 코드, Drizzle 설정, schema·migration·개발 seed 준비. 개발 DB의 migration 9개가 저장소 이력과 일치함을 읽기 전용으로 확인 |
| 수영장 모델 | 수영장, 운영시간, 자유수영 일정·회차·요금, 날짜별 휴관, 이미지·시설 schema 존재 |
| 서버 조회 | Pool Repository·Service, Drizzle 기반 조회 타입 구현 |
| 오늘 상태 | 기본 상태 계산 테스트 14개 구현. 일정 미확인은 `UNVERIFIED`로 처리. 상세 ID 검증 테스트를 포함한 전체 테스트는 25개 |
| 상세 페이지 | 실제 조회와 이름·주소·상태·회차·운영시간·일일/월 요금·공통 안내 표시. 양의 10진수 정수 ID만 허용하고 형식 오류·범위 초과·없는 ID는 404 처리 |
| 탐색 | 홈은 자리 표시 화면. 검색 결과 페이지와 검색 기능 미구현 |
| 공용 UI·mock 화면 | 토큰은 준비됐지만 확장 공용 UI와 전체 MVP mock 화면은 미구현 |
| 개인 기능 | 인증·관심 수영장·후기·정보 제보·마이페이지 미구현 |
| 배포·운영 | 저장소에 GitHub Actions workflow 없음. Vercel 연결·main 보호·모니터링은 별도 확인 필요 |
| 단계 1 진행 | A·B 완료, B의 수정은 PR #19로 `main` 병합. C의 데이터 계약·mock 시나리오는 로컬 임시 문서에 정리 완료. D·E 미착수 |

### 문서와 구현의 차이

- `github-ci.md`의 현재 상태에는 Vitest와 `test` 스크립트가 미구현으로 적혀 있으나, 실제 코드에는 존재한다. `typecheck` 스크립트는 없으므로 현재는 `pnpm exec tsc --noEmit`을 사용한다.
- 상세 조회 연결은 구현됐지만, 오늘 남은 시간과 입장 마감·회차 조건·정보 출처·확인일을 중심으로 한 상세 화면은 아직 완성되지 않았다.
- 상태 계산에는 수영장 자체 비활성 상태, 입장 마감, 부분 운영 변경, 정보 최신성 판단이 아직 충분히 반영되지 않았다.
- 현재는 회차가 없으면 일반 운영시간을 계산에 사용한다. 시간표 누락과 운영시간 전체 자유수영을 어떻게 구분할지 추가 검토가 필요하다. 동남스포피아 seed는 확인된 전체 이용 시간 범위를 회차에 저장하는 현재 방식을 유지한다.

위 차이는 남은 작업으로 기록한다. 이 문서 작성만으로 기존 설계나 데이터 처리 규칙을 변경하지 않는다.

## 3. 단계별 개발 순서

참고 자료의 개발 단계 흐름만 활용하고, 화면·데이터·기술 선택은 SwimFind 기준 문서를 따른다.
모든 화면의 UI를 먼저 검토하되, 실제 기능 연결은 공개 탐색 → 인증·관심 → 후기 → 제보 순서로 진행한다.
각 단계 안에서도 한 번에 한 작업만 수행한다. 후속 단계의 서버 기능을 미리 구현하지 않는다.

### 단계 1 — 기존 기반 확인과 작업 준비

왜: 이미 만든 기반을 다시 만들지 않고, 화면 검토와 실제 기능 연결의 출발점을 명확히 한다.

무엇을·어떻게:

- [x] 현재 상세 페이지의 정상 조회·없는 ID의 404·요일/가격/운영시간 표시를 브라우저에서 최종 확인한다.
- [x] 2절의 구현 상태와 미확인 사항을 갱신한다. 기존 schema·migration·seed를 임시 화면용으로 변경하지 않는다.
- [x] 기존 조회 타입을 바탕으로 UI가 받을 데이터와 mock 시나리오를 정리한다. 아직 없는 후기·제보 등의 화면 타입은 해당 화면을 만들 때 최소 범위로 정의한다.
- [ ] 초기 CI·Preview 준비 작업은 5절과 함께 진행한다.

완료 기준: 구현·검증·병합·배포 상태를 구분하고, 기존 실제 조회 흐름을 유지한 채 UI 개발을 시작할 수 있다.

### 단계 2 — 확장 공용 UI 전체 준비

왜: 전체 화면의 UI/UX를 빠르게 확인하려면 입력·버튼·피드백 표현이 일관된 기반이 필요하다.

무엇을·어떻게:

- [ ] 기존 색상·spacing·radius 토큰을 점검하고 필요한 typography·상태 표현을 정리한다.
- [ ] `Button`, `Input`, `Textarea`, `Badge`, `Card`, `Avatar`를 준비한다.
- [ ] `Select`, `Modal`, `Toast`를 준비한다.
- [ ] 로딩 표시·Skeleton·빈 상태·오류 안내 UI를 준비한다.
- [ ] 공통 페이지 컨테이너·헤더·내비게이션 등 화면 골격을 준비한다. 실제 화면에 필요한 경로부터 연결한다.
- [ ] 공용 UI는 `components/ui`에 두고 CSS Modules·CSS Variables를 사용한다. CVA는 variant가 여러 개인 컴포넌트에만 적용하고 단순 조건에는 clsx를 사용한다.
- [ ] 기본·포커스·비활성·오류·처리 중 등 해당 컴포넌트에 필요한 상태를 확인한다. Modal은 키보드 조작·포커스 이동과 복귀·닫기 동작을 확인한다.
- [ ] 공용 UI의 기본 상태와 조합을 로컬에서 확인할 수 있는 검토 화면을 준비한다. 검토 도구를 위해 별도 패키지를 먼저 설치하지 않는다.

완료 기준: 위 확장 공용 UI를 실제 화면에 조합할 수 있고, 모바일·데스크톱·키보드 환경에서 기본 동작을 확인했다. 공용 UI는 수영장 상태 계산이나 DB 접근을 포함하지 않는다.

### 단계 3 — 모든 MVP 화면의 mock UI/UX 확인

왜: 인증·업로드·저장 기능을 연결하기 전에 화면의 정보 우선순위와 이동 흐름을 빠르게 검토한다.

무엇을·어떻게:

- [ ] 공개 탐색: 홈·검색 결과·상세 화면을 만들고 이름·지역·현재 위치 탐색 진입과 상세 이동을 확인한다.
- [ ] 상세 보조 영역: 전체 일정·일반 운영시간·가격·이용 조건·휴관·출처·확인일·이미지·시설·FAQ·강습 안내·후기 요약을 표현한다.
- [ ] 개인 기능: 로그인·관심 목록·마이페이지와 로그인 전후 화면 복귀를 표현한다.
- [ ] 후기: 목록·작성·수정·작성 완료·삭제 확인·작성자 프로필·다른 후기·내 후기를 표현한다.
- [ ] 제보: 정보 수정 제보·미등록 수영장 등록 요청·접수 결과·내 제보·검토 상태를 표현한다.
- [ ] 운영자 검토: 제보 목록·내용 비교·승인/반려 흐름을 표현한다. 별도 통계 대시보드 등은 추가하지 않는다.
- [ ] `PoolCard`, `PoolStatusBadge` 등 도메인 UI는 `features`에 두고 공용 UI를 조합한다.
- [ ] 정상·로딩·빈 목록·조회 실패·정보 미확인·휴관·종료·로그인 필요·폼 오류·제출 실패 시나리오를 확인한다.
- [ ] 모바일 우선으로 화면을 검토하고 데스크톱·키보드 접근도 확인한다. 검색 조건·뒤로가기·입력 유지·다음 행동을 점검한다.

완료 기준: 모든 MVP 화면과 주요 행동을 mock으로 확인하고 UI 피드백을 반영했다. 이 완료는 실제 로그인·조회·저장·업로드 기능의 완료를 뜻하지 않는다.

### 단계 4 — 공개 탐색과 오늘 이용 정보 실제 연결

왜: mock으로 확인한 핵심 경험을 실제 DB의 수영장 데이터로 제공하고, 잘못된 이용 판단을 막는다.

무엇을·어떻게:

- [ ] 홈의 이름·지역 검색과 `/pools` 검색 결과를 Repository·Service에 연결한다. 검색 조건은 URL `searchParams`에 유지한다.
- [ ] 지역 검색은 현행 주소 데이터로 가능한 범위부터 구현하고, mock 검색 결과를 실제 결과로 교체한다.
- [ ] 목록에서도 같은 Service의 오늘 상태를 사용한다. 필요한 데이터를 목록 조회에 함께 가져오고, 수영장마다 상세 조회를 반복 호출하는 방식은 피한다.
- [ ] 기존 상세 조회를 검토한 UI에 연결하고, 오늘 적용 일정과 남은 이용 시간을 Service에서 구성한다.
- [ ] 비활성 수영장의 공개 조회 정책, 시간표 누락, 입장 마감·회차별 조건, 전일 휴관·부분 운영 변경을 검토하고 계산·표시에 반영한다.
- [ ] `UNKNOWN`·`NOT_OPERATED`를 구분한다. 정보가 부족하면 `UNVERIFIED`, 일정 없음이 확인된 근거가 있을 때만 `NO_SCHEDULE`을 사용한다.
- [ ] 정보 출처·확인일·공식 홈페이지를 표시한다. 정보 최신성 판단 기준과 필요한 검증 데이터는 별도로 합의한다.
- [ ] 일정 적용 기간·휴관 우선순위·시작/종료·입장 마감 경계 테스트를 보완하고, 실제 조회의 로딩·빈 결과·오류·404를 확인한다.

완료 기준: 로그인 없이 홈 → 검색 → 상세 흐름을 실제 데이터로 이용할 수 있다. 사용자가 오늘 시간·가격·조건·예외를 확인할 수 있고 주요 판단 규칙이 테스트로 검증된다.

### 단계 5 — 위치·이미지·보조 정보 실제 연결

왜: 화면에 표현한 위치·시설 등의 정보를 실제 탐색과 방문 판단에 사용할 수 있게 한다.

무엇을·어떻게:

- [ ] Browser Geolocation API와 우리 DB의 좌표로 주변 탐색을 구현한다.
- [ ] NAVER Maps는 DB 검색 결과의 지도 표시와 위치 확인에 사용한다.
- [ ] 위치 권한 거부 시 지역 직접 선택으로 이어지도록 한다.
- [ ] 이미지·시설·공식 안내·길찾기를 연결하고, 확인되지 않은 정보는 mock 대신 미확인 상태로 표시한다.
- [ ] FAQ·강습 안내는 핵심 정보보다 낮은 우선순위로 연결한다. 필요한 데이터 구조는 실제 확인된 요구사항에 맞춰 설계한다.

완료 기준: 이름·지역·현재 위치로 후보를 비교할 수 있고, 위치 권한을 거부해도 핵심 흐름을 이용할 수 있다. 시간표상 이용 가능을 실시간 입장 보장으로 표현하지 않는다.

### 단계 6 — 인증·관심 수영장 실제 연결

왜: 검토한 로그인·관심 UI를 실제 사용자별 데이터와 안전하게 연결한다.

무엇을·어떻게:

- [ ] Better Auth와 필요한 사용자·세션 모델을 설계하고 migration을 검토한다.
- [ ] 로그인·로그아웃과 원래 화면 복귀를 구현한다.
- [ ] 관심 수영장 등록·해제·목록을 구현하고 사용자와 수영장 조합의 중복을 막는다.
- [ ] 서버에서 인증과 소유권을 확인하고, 목록은 저장 당시가 아닌 현재의 오늘 상태를 표시한다.
- [ ] 마이페이지의 기본 프로필·관심 목록 진입점을 연결한다.

완료 기준: 공개 탐색은 계속 비로그인으로 이용 가능하며, 로그인 사용자는 자신의 관심 수영장을 저장·해제·재조회할 수 있다.

### 단계 7 — 후기·이미지 실제 연결

왜: 공식 안내만으로 알기 어려운 실제 이용 경험으로 방문 판단을 보완한다.

무엇을·어떻게:

- [ ] 후기·후기 이미지 모델과 조회·작성·수정·삭제 권한을 구현한다.
- [ ] 후기 조회는 공개하고, 작성·변경은 로그인한 작성자에게 허용한다.
- [ ] React Hook Form·Zod를 폼 개발 시점에 적용하고, 변경은 Server Action → 검증 → Service → Repository로 처리한다.
- [ ] S3 presigned URL로 이미지 업로드를 구현하고 파일 제한·사용자 소유권·후기당 최대 5장을 검증한다.
- [ ] 작성자 프로필·다른 후기, 마이페이지의 내 후기를 연결한다.
- [ ] 제출 실패 시 입력을 유지하고 중복 제출을 방지한다.

완료 기준: 비로그인 사용자는 후기를 읽을 수 있고, 작성자는 자신의 후기를 관리할 수 있다. 과거 혼잡 경험을 실시간 혼잡 정보로 표시하지 않는다.

### 단계 8 — 정보 제보·운영자 검토 실제 연결

왜: 운영 정보의 오류와 변경을 수집하고, 검증된 데이터만 공식 정보로 제공한다.

무엇을·어떻게:

- [ ] 로그인 사용자의 정보 수정 제보와 미등록 수영장 등록 요청을 구현한다.
- [ ] 근거·수정 제안·처리 상태를 저장하고 마이페이지에서 내 제보를 조회한다.
- [ ] 운영자의 검토·승인·반려 절차와 권한을 구현한다.
- [ ] 승인 후 공식 정보와 확인일은 검증을 거쳐 별도로 수정한다. 제출만으로 자동 반영하지 않는다.

완료 기준: 접수 성공과 검토 완료가 구분되며, 미검증 제보는 공식 정보로 노출되지 않는다.

### 단계 9 — 통합 검증과 출시 준비

왜: 개별 기능의 정상 동작뿐 아니라 실제 사용자 흐름과 운영 환경을 검증한다.

무엇을·어떻게:

- [ ] 홈 → 검색 → 상세 → 오늘 이용 정보 확인을 Playwright로 검증한다.
- [ ] 로그인 복귀·관심 저장·후기 작성·제보 접수와 각 흐름의 실패·재시도를 검증한다.
- [ ] 미확인·휴관·종료·위치 권한 거부·없는 ID·권한 없는 변경 등 주요 예외를 확인한다.
- [ ] 모바일·키보드 접근·이미지·쿼리·메타데이터·SEO·성능을 점검하고 실제 측정 결과에 따라 개선한다.
- [ ] 운영 DB·초기 import·migration 적용 및 복구 절차·환경 변수·Vercel Production 배포를 확인한다.
- [ ] Sentry·PostHog를 필요한 범위에서 연결하고, 배포 후 핵심 흐름을 다시 확인한다.
- [ ] 공개 환경에 mock 데이터·가짜 로그인·가짜 제출 성공이 남아 있지 않은지 확인한다.

완료 기준: 공개할 기능이 실제 운영 데이터와 권한 기준으로 동작하고, 핵심 흐름·주요 예외·오류 추적·배포 상태를 확인했다.

## 4. mock 개발과 실제 연결의 경계

- 단계 1-C에서 기존 `PoolDetailResult`의 기본 정보·오늘 상태·운영시간·일정·회차·휴관·요금과 화면 표시 여부를 대조했다. 상세 계약에 없는 이미지·시설·후기·제보는 해당 기능 단계에서 연결한다.
- `null`은 값 미확인, 빈 배열은 조회된 row 없음으로 구분한다. 가격 기록 없음은 무료가 아니며, 입장 마감은 값이 있는 회차에만 표시한다.
- `NO_SCHEDULE`은 현재 상태 계산 함수가 반환하지 않는 UI 검토 시나리오다. 입장 마감에 따른 상태 변경과 부분 운영 변경은 단계 4에서 검토한다.

- mock 데이터는 UI 검토용으로 분리한다. 서버 Repository에 가짜 row를 넣거나 개발 seed를 mock 화면마다 다시 실행하지 않는다.
- 기존 Drizzle 기반 타입을 재사용하되, 아직 없는 도메인은 UI에 필요한 최소 타입만 정의한다. 전체 DB 모델·API 응답·전역 상태를 미리 확정하지 않는다.
- 화면이 받을 데이터와 사용자 동작을 분리해, 실제 연결 시 UI를 다시 만들지 않고 조회·저장 부분을 교체할 수 있게 한다. 과도한 공통 provider나 저장소 추상화는 추가하지 않는다.
- 상태 mock은 시나리오별로 준비한다. UI에 자유수영 상태 계산을 새로 구현하지 않고, 실제 연결 후에는 Service 결과를 사용한다.
- 기존 상세 페이지의 실제 조회 경로와 mock 검토 환경을 구분한다. 실제 조회 기능을 없애거나 전체 앱을 가짜 데이터로 바꾸지 않는다.
- 로그인·저장·업로드·운영자 검토는 mock 단계에서 화면 행동만 모의한다. 실제 인증·DB 반영으로 오해하지 않도록 검토 환경을 명시한다.
- 공개 탐색 화면부터 개인 화면·운영자 검토까지 모두 mock으로 확인하되, 기능 연결은 단계 4~8 순서를 따른다.
- UI 검토 완료 후 필요한 요구사항 변경을 정리한다. DB schema 변경은 별도 승인·migration 절차를 거쳐 진행한다.

## 5. 각 단계와 함께 진행할 엔지니어링 작업

이 작업들은 마지막까지 미루지 않고 관련 기능을 구현하는 시점에 함께 진행한다.

- [ ] 초기: `typecheck` 스크립트와 GitHub Actions CI를 구성한다. `pnpm install --frozen-lockfile` → Biome → 타입 검사 → `pnpm test --run` → build 순서로 검증한다.
- [ ] PR 검증 기반: Vercel Preview를 개발 DB에 연결하고, 비밀값은 환경별로 관리한다. main 보호와 CI 필수 조건을 적용한다.
- [ ] 공개 탐색 완성 시: Playwright로 홈 → 검색 → 상세 흐름과 주요 예외를 로컬 검증한다. 안정화 후 별도 CI job을 추가한다.
- [ ] 배포 준비 시: 운영 DB와 개발 seed를 분리하고, 운영 초기 import·migration 적용·복구 절차를 확인한다.
- [ ] 공개 배포 전: Sentry 오류 추적과 PostHog의 핵심 탐색 지표를 필요한 범위에서 연결하고, 비밀값·개인정보 수집 설정을 검토한다.
- [ ] 운영 연결 시: main → Vercel Production 자동 배포를 확인한다. 실제 사용자에게 공개하는 범위는 해당 단계의 완료 기준을 충족한 기능으로 정한다.

TanStack Query는 추가 조회나 optimistic update가 필요한 시점에 적용한다. 공개 데이터 최초 조회는 Server Component → Service → Repository 흐름을 유지한다.

## 6. 작업과 완료 상태 관리

- 한 번에 다음 기능 하나를 선택하고, 왜 필요한지 → 무엇을 만들지 → 어떻게 구현할지 설명한 뒤 승인된 범위에서 진행한다.
- 각 작업에는 목표·선행 작업·구현 체크리스트·수락 기준·검증 항목을 기록한다. 별도 Task 파일을 자동으로 만들기보다 기존 Issue 템플릿과 로드맵을 우선 사용한다.
- Issue·PR은 실제 저장소 템플릿을 따른다. 관련 테스트를 기능 커밋에 포함하고, 한국어 Conventional Commit을 사용한다.
- PR에는 실제 수행한 검사와 미확인 항목을 구분한다. mock UI 완료·실제 기능 연결·로컬 검증·main 병합·배포를 같은 완료 상태로 취급하지 않는다.
- migration은 schema 수정 → generate → SQL 검토 → 개발 DB migrate → 실제 DB 확인 순서로 진행한다. 적용된 migration은 수정·삭제하지 않는다.
- 단계별 체크박스는 검증 후 갱신한다. 기능 작업으로 정책이 바뀌면 관련 기준 문서와 이 로드맵의 상태도 함께 검토한다.

바로 다음 작업은 단계 1-D의 초기 CI 구성이다. 이어서 단계 1-E의 Preview·main 보호를 확인한 뒤 단계 2의 공용 UI 준비를 시작한다.

## 7. MVP 이후 검토

예약·결제, 강습 전용 검색·추천, 운동 기록, 커뮤니티·채팅, 실시간 혼잡도 등은 [MVP 제외 범위](product/mvp.md#15-out-of-scope)에 따라 보류한다.

새 기능은 “오늘 갈 수 있는 수영장을 찾는 데 직접 도움이 되는가?”와 실제 사용자 요구를 기준으로 검토한다. 전체 화면의 mock 검토를 먼저 하더라도 공개 탐색의 실제 연결이 핵심 경험의 첫 완료 지점이며, 개인화·후기·제보의 실제 연결은 제품 문서의 후속 MVP 순서를 따른다.

참고 자료는 개발 진행 단계에만 활용한다. 기술·테스트·품질 기준과 출시 범위는 SwimFind 문서를 따르며, 일정과 성능 목표는 실제 작업 범위와 측정 결과를 바탕으로 정한다.
